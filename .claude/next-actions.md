## 次に cold start を取るときの手順 (2026-09-24 15:xx・**前の版は間違っていた**)

**About を読む手順は捨てること。**2026-09-24 に再起動して試した結果、
**「最初の描画」は cold start を測れない**と分かった (ADR-0157)。
時計が `run()` の 1 行目で始まるので、**カーネルの exec と dyld の読み込みが
時計の外**にある —— そこが cold と warm の差そのもの。
実測: 再起動直後 **451 ms** / その次の起動 **431 ms**。差は 4%。

**直した。**読み取り値が `started_at_unix_ms` (時計開始の壁時計時刻) を持つようになり、
外のストップウォッチが引き算できる。**手順はこう:**

```
1. 再起動する前に、新しいバイナリを 1 回起動しておく  ← Gatekeeper を済ませる
2. PC を再起動
3. 上がったら いちばん最初に:
     sh scripts/measure-cold-start.sh
```

**2 の前に 1 を飛ばすと、cold start ではなく Gatekeeper を測る。**
実測: 新しいビルドの初回 `loading` **3108 ms** / それ以降 **15-17 ms**。

**3 は「最初に」。**他の手段でアプリを開いた時点でサンプルを使い切る (1 起動に 1 回)。
スクリプト自身がアプリを起動する必要がある (環境変数を渡すため・`open` 経由では渡らない)。

**warm の実測 (2026-09-24・比較の土台)**:
```
total 404-433 ms  /  inside 388-418 ms  /  loading 15-17 ms
```

**v0.19 の枠はこれだけでは埋まらない。**残りは項目 2 ——
**実在の接続でスキーマツリーが埋まるまでの時間**と、**Run から最初の 1 行まで**。
roadmap が「合成ではなく実物で」と要求しているので、**どの接続を使うかは user が選ぶ**。
**未決の 2 点**: どの接続を使うか / 時間をどう測るか

### この機体について (2026-09-23 実測・dbboard 外)

- **Remote Control の接続が切れている**セッションがある。**プロセスは生きている。**
  切れた側は気づかない (状態を知る公開口が無い)。**エージェントから `reconnect` は叩けない**
- **この mac mini は SSH を受けていない** (ポート 22 に listen なし・`sshd` なし)。
  **有効化していない — 持ち主の判断。**無人時に外から入る経路は現状これしかない
- **【解決済み・2026-09-24 15:20】回線が終日不安定だった原因は、死んでいる有線を
  優先していたこと。LAN ケーブルを抜いて直った。**

  **症状**: GitHub もそれ以外も到達できたりできなかったり。失敗はきっかり 4.01 秒
  (接続タイムアウト)。ゲートウェイへの ping は 0% ロス・0.48ms で完璧。
  traceroute はゲートウェイが `!N` (経路が無い) を返す。**他の PC は平気。**

  **原因**: 有線 (en0=`.17`) と無線 (en1=`.16`) が**同じサブネットで両方 active**、
  既定経路が 2 本。macOS の優先順位は `(1) Ethernet (2) Wi-Fi` なので、
  **全通信が死んでいる有線へ流れていた。**

  ```
  有線 (en0) から 8.8.8.8   100% ロス / github 失敗
  無線 (en1) から 8.8.8.8     0% ロス / github 200 (0.53 秒)
  ```

  **物理層は無実だった**: en0 は `1000baseT full-duplex`・`Ierrs 0 Oerrs 0 Coll 0`。
  ケーブルや端子が傷んでいれば CRC エラーが出るか 100baseTX に落ちる。どちらも無い。
  **ルーター側でこの有線ポート (か `.17`) が外に出られない状態。**
  有線を使いたければ、ハブのポートを変えるかルーターの設定を見ること。

  **切り分けはこの 3 手で付く** (次に同じ症状が出たら):
  ```sh
  netstat -rn -f inet | grep '^default'          # 既定経路が 2 本なら黒
  ping -c 3 -S <有線の IP> 8.8.8.8                # 経路ごとに ICMP
  curl --interface en1 -o /dev/null -w '%{http_code}\n' https://github.com/
  ```

  **私が朝に立てた診断は 2 つとも外れていた。**「IP ごとの当たり外れ」も
  「ルーターの経路情報が壊れている」も、観測した現象は本物だったが
  **原因の場所を取り違えていた。**「40 分後に通った」のは、たまたま無線側へ
  流れた瞬間があっただけ。**ゲートウェイが健全なのに外へ出られないときは、
  まず経路が何本あるかを見ること。**

### Mac で変わること

**消える地雷** (どれも Windows 固有):
libSQL の teardown segfault (`0xc0000005`) と `cargo-test-serialised.sh` の 1 回リトライ、
Norton の隔離、`link.exe 1318` / `os error 112` (ディスク枯渇)、scrypt の 256MiB×並列、
release exe が起動中でロックされて `cargo build --release` が落ちる件、GitHub Desktop の force push。
**スクリプトと直列リストは消さない** — CI の windows runner が同じ道を通る。

**効かなくなるルール**: `pii-scan.sh` の `windows-home-path` は Windows のホームパスだけを見ている。

**できなくなること**: Windows の `.exe` を手元でビルドできない →
**公開物の PII 目視確認は CI 成果物をダウンロードして**行う。
