# 0022 — 手で書いたクエリの結果も、行が特定できるなら編集できるようにする

- 状態: 未着手（次のアップデートの企画候補）
- 出典: 2026-08-16 のセッション。`SELECT * FROM <db>.customers LIMIT 100` の結果を
  ダブルクリックしても編集にならない、という指摘。
- 関連: ADR-0042（インライン編集）、ADR-0082（拡張エディタ）、ADR-0102（ENUM）

## いまどうなっているか

`QueryPanel.svelte` の `editContext` は、**サイドバーからテーブルを開いた結果**
（"Select top 100"）のときだけ組み立てられる。手で書いたクエリを実行するか、
履歴から再実行すると `editTable` が消えるので、結果は常に読み取り専用になる。

判定に使っているのは「どこから実行されたか」であって、「行が特定できるか」ではない。

## なぜ今の形になっているか

任意の SQL の結果は、どのテーブルのどの行なのかが確定しない。確定しないまま
UPDATE を組み立てると、意図しない行を書き換える。だから安全側に倒して、
出どころが分かっている browse だけを編集可能にした。

**この判断自体は正しい。**変えたいのは判定の粒度であって、安全側に倒す方針ではない。

## 何を変えるか

判定を「出どころ」から「**行が特定できるか**」に変える。

編集可能にできる条件（すべて満たすとき）:

1. 単一テーブルの `SELECT` である（JOIN・サブクエリ・集合演算を含まない）
2. 集計・`GROUP BY`・`DISTINCT` を含まない
3. 選択列に**主キーが全部含まれている**（`SELECT *` は含まれているとみなせる）
4. 対象テーブルに主キーが宣言されている（既存の `noPk` と同じ扱い）

編集できないケースは今までどおり読み取り専用にする:

- JOIN — 1 行が複数テーブルに対応するので、どこを書くか決まらない
- 集計 — 対応する行が存在しない
- 主キーが結果に無い — WHERE を組めない
- 式・関数の結果列 — 書き戻す先が無い（列単位で編集不可にする）

**「いつでも編集できる」は原理的に到達できない。**到達できるのは
「行が特定できるときは、実行経路によらず常に編集できる」まで。

## 実装の見通し

- SQL の解析が要る。正規表現で済ませると `FROM (SELECT ...)` のような形を
  取りこぼすので、パーサを入れるかどうかは ADR を書いて決める
  （新規クレート導入なので `docs/decisions.md` 行き）
- 判定は `dbboard-core` 側に置く。UI の分岐に業務ロジックを持たせない
- 誤判定の代償が非対称であることを設計に反映する。
  **編集可能にすべき結果を読み取り専用にするのは不便で済むが、逆は書き換え事故になる。**
  判定に迷ったら読み取り専用に倒す

## 編集できないときに、どう案内するか

「行が特定できない」で終わらせると、利用者から見れば理由の分からない読み取り専用でしかない。
**編集できる形に持っていく導線まで含めて 1 つの機能**とする。

### A. 主キーを裏で自動補完する（既定）

`SELECT name FROM customers` のように主キーが選択列に無いだけの場合、実行時に主キー列を
足して取得し、**隠し列**として保持する。表示は利用者が書いたとおりのままで、編集だけが通る。

補完したことは画面に小さく出す。書いた SQL と実際に走る SQL が違う状態を黙って作らない。

### B. 書き換えを提案する（A が使えないとき）

`DISTINCT`・`GROUP BY`・JOIN のように、主キーを足すと**結果そのものが変わる**形では
自動補完できない。この場合は理由と併せて、**編集可能になる SQL を提示して「これで実行し直す」**
を出す。押すかどうかは利用者が決める。勝手には実行しない。

### C. 主キーが無いテーブルも救う

主キーが宣言されていなくても、**UNIQUE かつ NOT NULL の索引**があれば行は特定できる。
いまは主キーだけを見ているので、ここを広げると対象テーブルが増える。
複数該当する場合は列数の少ないものを選ぶ。

### D. 読み取り専用の理由を必ず出す（先行実装可）

現状、読み取り専用の結果をダブルクリックしても**なぜ編集できないのかが画面に出ない**。
無言で値ダイアログが開くだけなので、仕様を知らないと不具合に見える。実際そう報告された。

`noPk` のときに出している読み取り専用の理由表示を、他の読み取り専用ケースにも広げる。
A・B・C と独立に先行できるうえ、**利用者が実際に困っているのはここ**なので優先度は高い。

## 完了条件

- 単一テーブル `SELECT *` の結果が、サイドバー経由と同じように編集できる
- 主キーを選んでいない単一テーブル `SELECT` が、自動補完で編集できる（A）
- JOIN・集計の結果は読み取り専用のままで、書き換え案が出る（B）
- 主キーが無く UNIQUE NOT NULL 索引があるテーブルが編集できる（C）
- **読み取り専用の結果には、必ずその理由が画面に出る（D）**
- 判定ロジックの単体テストが、上の 4 条件と 4 つの除外ケースを網羅する
