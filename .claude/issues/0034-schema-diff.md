## この issue の形

**エンジンと UI を分けた。** 比較ロジックは純粋・テスト可能で、画面のどこに出すかに
影響されない。一方で「どこに出すか」は `CLAUDE.md` が

> **AI が先回りして決めない。** 見た目の方向性は人が決める領域であり、
> AI が埋めた既定値はそのまま既成事実になる。

と定めている領域。なので**エンジンだけ先に出し、UI は判断を待つ**。

## 決めたこと（ADR-0148 に全文）

差分ツールの間違え方には方向がある。**「同じだ」と言って間違える方が高い** —
余計な差分は読み手の二度見で済むが、見逃しは移行そのものを壊す。全部の判断をその向きに倒した。

1. **同一エンジン限定。ただし拒否はこの層より上**（この層は 2 組のテーブル情報しか知らない）。
   異種間比較は**型の対応表**という別機能で、Database Workspace 計画の band 7
   (Compatibility Scan) に既に居場所がある
2. **テーブルは修飾名で照合**（`public.orders` と `staging.orders` は別物）、**列は名前で照合**
3. **型はエンジンが綴ったまま比較** — 正規化なし、大文字小文字の畳み込みなし。
   `VARCHAR(255)` と `varchar` を同じと判定するのはエンジンの知識で、
   正規化の規則 1 つ 1 つが見逃しの機会
4. **列順は差分にしない**（順序違いはノイズで本物を埋める）。**主キーの順序は比較する**
   （`(a, b)` と `(b, a)` は別物を索引する）
5. **列と主キーのみ。インデックス・制約は入れない** — `describe_table` は全アダプタで列を返すが、
   インデックスは取得手段がエンジンごとに違い、11 個のうち何個が答えられるか未確認。
   一律に手に入る半分を先に出す（残りは additive）
6. **片側にしか無いテーブルは 1 回だけ報告** — 「列が全部無いテーブル」としては報告しない。
   1 つの事実に 1 つの所見。差分の無いテーブルは報告に出ない（在庫表ではない）
7. **出力は順序が決まっている** — 実行のたびに並びが変わる差分は、前回と比較できない
