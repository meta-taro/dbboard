# 0029 — 10,000 行を作らない: 大きな結果セットのページング

- 状態: 未着手（方向だけ確定。設計はこれから）
- 枠: `docs/roadmap.md` Near slots の **v0.15 — Everyday work**（v0.14 から移った半分）
- 関連: ADR-0142（本 issue を生んだ調査）、ADR-0141（計測基盤）、ADR-0046（読み取り専用の soft cap）

## なぜこれなのか

v0.14 は「速くなった版」ではなく「速さが言えるようになった版」だった。その数字を
v0.15 で使おうとして最初に分かったのは、**測った範囲に効く最適化が無い**ことだった
（ADR-0142）。

- startup 群は合計 1ms 程度。窓が出る費用に比べれば誤差。
- 読み取り専用パスは 3 アダプタとも既に上限で打ち切っている。
- `query_10k` の 4.4ms は 143 ns/行 + 37 ns/値 の直線で、**この表現の値段**。
  コードの誤りではないので、書き換えても数%しか動かない。しかも計測機の
  run 間ばらつきが 1.5〜1.8 倍あるので、その数%は見えない。

残る唯一の大きな梃子は、**作る行を減らすこと**。グリッドが一度に見せるのは
数十行で、`MAX_RESULT_ROWS` は 10,000。差は 200 倍ある。

## 何を決める必要があるか

1. **どこで切るか。** アダプタ（SQL に LIMIT/OFFSET を足す・カーソルを持つ）か、
   コア（全件取ってから窓を切る）か。後者は今と同じ費用なので、意味があるのは前者。
   ただし SQL を書き換えるのは、手で書いた SQL を実行する経路では**副作用が見える**
   （`LIMIT` を自分で書いた人の意図と衝突する）。
2. **カーソルの寿命。** ページを跨いで接続を握るのか、ページごとに投げ直すのか。
   握るなら、切断・再接続・タブを閉じたときの後始末が要る。読み取り専用パスの
   Postgres カーソルは既にトランザクション内で完結させているので、その形が参考になる。
3. **契約への影響。** `QueryResult` は Tauri IPC を JSON で渡り、`docs/api-contract.md`
   は v1.0 で凍る。ページング用の形（総件数・カーソル・次ページ有無）を足すなら、
   **凍る前に**足す必要がある。web 側（`dbboard-web`）にも同じ contract がある
   （CLAUDE.md の Pacing Note: contract に触るなら両 repo の `decisions.md` に ADR）。
4. **総件数を出すか。** `COUNT(*)` を別に投げると 2 倍のクエリ、出さないと
   スクロールバーが嘘をつく。どちらを選ぶかは UI の約束の問題。

## 測り方（先に決めておく）

`crates/dbboard-bench` に点を足す前に、**何が「速くなった」なのかを決める**。
候補は「最初の 100 行が画面に出るまで」で、いまの `browse/first_page_100`（74µs）が
その原型。10,000 行の materialise を経由しなくなれば、この点は変わらず、
`result/query_10k` は**そもそも通らない経路**になる。

つまり成果は「4.4ms が 2ms になった」ではなく「4.4ms を払わなくなった」の形で出る。
baseline の点はそれに合わせて足す（消すなら `baseline_drift.rs` が止める）。

## やらないこと

- `truncate_rows` の書き換え（ADR-0142: 解放コストであって関数の問題ではない）
- `annotations.toml` の解析の最適化（ADR-0142: 遅くない。比較が間違っていた）
- 数%の差を狙う微調整（計測機の run 間ばらつき 1.5〜1.8 倍に埋もれる）
