# 0029 — 101 行目を見る手段が無い: 大きな結果セットのページング

> 旧題は「10,000 行を作らない」。その 10,000 行は最初から作られていなかった
> （ADR-0145）。題を実態に合わせた。

- 状態: 設計確定（ADR-0145）。実装はこれから
- 枠: `docs/roadmap.md` Near slots の **v0.16 — Everyday work**（v0.14 → v0.15 → v0.16 と送られた半分）
- 関連: ADR-0145（4 論点の決定）、ADR-0142（本 issue を生んだ調査）、ADR-0141（計測基盤）、
  ADR-0046（読み取り専用の soft cap）、ADR-0049（keyset ページングの初出＝dump）

## なぜこれなのか

v0.14 は「速くなった版」ではなく「速さが言えるようになった版」だった。その数字を
v0.15 で使おうとして最初に分かったのは、**測った範囲に効く最適化が無い**ことだった
（ADR-0142）。

- startup 群は合計 1ms 程度。窓が出る費用に比べれば誤差。
- 読み取り専用パスは 3 アダプタとも既に上限で打ち切っている。
- `query_10k` の 4.4ms は 143 ns/行 + 37 ns/値 の直線で、**この表現の値段**。
  コードの誤りではないので、書き換えても数%しか動かない。しかも計測機の
  run 間ばらつきが 1.5〜1.8 倍あるので、その数%は見えない。

残る唯一の大きな梃子は「作る行を減らすこと」——**と書いたが、これは間違っていた**。
設計前にコードを読んで分かったこと（ADR-0145）:

- browse クエリはフロントで既に `SELECT * FROM t LIMIT 100` に絞られている
  （`apps/desktop/src/lib/sql/build.ts` の `selectTopN`、`BROWSE_ROWS = 100`）
- `McpService::run_read_query` がさらに `DEFAULT_MAX_ROWS = 200` / 上限
  `MAX_MAX_ROWS = 1000` で丸める
- Postgres はその 1000 行すら投機的に作らない。`run_read_only_txn` が read-only
  トランザクション内で `DECLARE CURSOR` を張り `max_rows` で止める
  （Aurora DSQL だけ `DECLARE` 不可なので capped stream）

`MAX_RESULT_ROWS` は `query` の天井であって、**窓が辿る経路の天井ではない**。
200 倍は最初から払われていない。

**本当の欠落は「101 行目を見る手段が無い」こと。** 上限は常に打ち切りであって、
1 ページ目ではなかった。これは性能改善ではなく**機能の欠落**で、ページングの性能上の
性質は「ページあたり O(1) を保つ」の方である。

## 決めたこと（ADR-0145）

1. **どこで切るか → 生成される browse クエリだけ。** 手書き SQL には触らない。
   人が書いた `LIMIT` と道具が争う形になり、しかもその不一致が結果に見える。
   手書き経路は既存の truncated フラグのまま。
2. **カーソルの寿命 → 握らない（keyset）。** `ORDER BY <pk>` +
   `WHERE (k1,k2) > (v1,v2)` + `LIMIT n`。ページごとに投げ直し、前ページ最終行の
   キーだけを持ち回る。切断・タブを閉じた・放置の後始末が存在しなくなり、
   ページ間の挿入で行が境界を跨がない。
   **新規コードではない** — `crates/dbboard-core/src/dump/select.rs` の
   `build_select_page` が ADR-0049 以来これを組み立てている（複合キーの行値比較つき、
   SQLite 3.15+ / Postgres 両対応）。browse はこれを再利用する。
   主キーが無いテーブルは 1 ページ目のみ（その関数が既にそう契約している）。
3. **契約 → `QueryResult` に足す。凍る前に。** `has_more` とカーソルを optional
   フィールドとして `docs/api-contract.md` の形に追加する。IPC 側の `QueryOutput`
   だけに置くのは今は安いが、v1.0 の凍結後は同じ追加が破壊的変更になり、MCP 越しの
   エージェントは `truncated` だけ見て先に進めなくなる。
   **`dbboard-web` 側に同じ ADR が要る**（CLAUDE.md の Pacing Note）。
4. **総件数 → 出さない。`has_more` だけ。** 毎ページ `COUNT(*)` はクエリ 2 倍＋
   大きなテーブルで毎回フルスキャン、初回 1 回だけでも挿入で古くなり最初の描画が
   スキャンの分だけ遅れる。スクロールバーは「まだある」（真）を約束し、長さ
   （真でない）を約束しない。正確な数字は右クリックの `countRows` が既に答えている。

## 測り方（先に決めておく）

**成果は「4.4ms を払わなくなった」ですらない**（ADR-0145）。その 4.4ms は
最初から窓が辿る経路に無かった。`result/query_10k` は baseline に**そのまま残す** —
表現の値段を測る点であってアプリの経路を測る点ではなく、この作業で動かない。
消さない理由をここに書いておく（`baseline_drift.rs` が消すのを止めるが、
なぜ残すかは止めてくれない）。

足したのは「深いページが O(1) であること」を示す点 `browse/next_page_100`。
500 行のテーブルの**最後の**ページ（2 ページ目ではない — OFFSET は 2 ページ目では
安く、5 ページ目で高い）を keyset カーソルで読む。`first_page_100` と同じ
`adapter.query` 経由にしてあるので、2 つの数字の差はカーソルだけになる。

実測（2026-09-04、同じ Mac mini）: **first 71.6µs / next 70.3µs**。
深いページが浅いページより高くない、が keyset を選んだ理由そのものの証拠。
`result/query_10k` は 4.4ms のまま（ADR-0142 と一致）— この作業では動かない点。

CHANGELOG に書くのは**辿れるようになった行**であって、払わなくなったミリ秒ではない。

## やらないこと

- `truncate_rows` の書き換え（ADR-0142: 解放コストであって関数の問題ではない）
- `annotations.toml` の解析の最適化（ADR-0142: 遅くない。比較が間違っていた）
- 数%の差を狙う微調整（計測機の run 間ばらつき 1.5〜1.8 倍に埋もれる）
