## なぜこれなのか

結果グリッドは ADR-0035 以来 CSV と TSV を書き出せる。どちらも `exportValue` を通り、
**全てのセルが文字列に潰される**:

| セル | CSV が書くもの |
|---|---|
| `NULL` | `''`（空文字） |
| document（`{$json: …}`） | JSON の**文字列** |
| blob（`{$blob: …}`） | `<blob>` というリテラル |
| 数値・真偽値 | 表示用の文字列 |

表計算のセルには他に置き場が無いので、**Excel で開くファイルとしては正しい**。
機械が読み戻すファイルとしては正しくない — `NULL` と空文字を区別できない受け手は
行を復元できないし、document を引用符付き文字列で受け取った側はもう一度パースする羽目になる。

**JSON は CSV の句読点違いではない。型がそのまま残ることが存在理由。**

## 決めたこと（ADR-0146 に全文）

1. **行オブジェクトの配列** — `[{"id": 1, …}, …]`。`columns` + `rows` の形は
   API contract が既に提供している
2. **同名列は落とさず番号を振る** — `id`, `id:2`, `id:3`。`SELECT a.id, b.id` は普通の SQL で、
   JSON オブジェクトは同名メンバを 2 つ持てない。無名列は `column:<位置>`
3. **`$json` は外し、`$blob` は残す** — タグは「その転送形式が自力で表せない型情報」を運ぶもの。
   JSON は document を表せるのでタグは雑音、bytes は表せないのでタグが要る
4. **BOM は付けない** — CSV は Excel のために付ける（ADR-0035）。JSON パーサは BOM を拒否する。
   代わりにインデント付き・末尾改行（人も開くので）
5. **全体ではないときは、保存の確認がそう言う** — エクスポートは常にグリッドが持つ分だけを書いてきた。
   ADR-0145 以降それは「何ページかのうちの 1 ページ」が常態なので、黙っていると後で全件として読まれる。
   **CSV 側の同じ沈黙もこれで直る**

## 採らなかった案

- **`truncated` / `has_more` を包む wrapper オブジェクト** — 自己記述的になる代わりに、
  全ての受け手が封筒を剥がしてからデータに届くことになる。しかも 2 つのエクスポートで
  「エクスポートファイルとは何か」の答えが食い違う
- **ボタンの裏でページを歩いて全件書き出す** — Save と書かれたボタンが際限のない
  クエリ列を発行することになる。全件抽出は dump (ADR-0049) として既に意図的に存在する
- **JavaScript のために整数を文字列にする** — 2^53 を超える `i64` は `JSON.parse` で精度を失うが、
  書かれるテキストは正確な桁を持ち、JavaScript 以外の受け手は正しく読む。
  1 つのランタイムのために全ての数値を引用符で包むと、数値を期待する全ての受け手が壊れる
